`@portone/docx-editor/core` provides programmatic DOCX import and export without mounting an
editor. It returns a ProseMirror document together with an opaque session that retains the rest of
the DOCX package.

## Import and export

Keep the session returned by `importDocx` and pass it back to `exportDocx` with the original or
transformed document:

```ts
import { exportDocx, importDocx } from "@portone/docx-editor/core";

const { doc, session } = importDocx(source);
const bytes = exportDocx(doc, session);
```

The core functions accept an `ArrayBuffer` or `Uint8Array`. The React component also accepts a
`Blob` or `File` and reads it before import.

The session belongs to the imported document and must not be constructed or modified by consumers.
Use `documentNumbering(session)` and `documentPartPath(session)` for the package information
exposed by the public API.

## Server environments

Reading a DOCX means reading the XML inside it, and that needs a parser. Browsers have one.
Anywhere else, pass one in:

```ts
import { JSDOM } from "jsdom";
import { importDocx } from "@portone/docx-editor/core";

const { DOMParser } = new JSDOM().window;

const { doc, session } = importDocx(source, { xmlParser: new DOMParser() });
```

`importDocx`, `exportDocx`, and `onlyCommentsChangedBy` all take `xmlParser`, and the parser one
of them is given reads every part it touches, including both of the files `onlyCommentsChangedBy`
opens for itself.
The option asks only for `parseFromString(source, "application/xml")` returning a DOM document.
The package bundles no parser of its own, so the choice is yours: jsdom is the obvious one on a
long-running Node server, while on serverless functions it adds noticeable bundle weight and
cold-start time and edge runtimes cannot run it at all, which is where a lighter implementation
earns its keep.

Installing a `DOMParser` global instead works, and every call then leaves the option out:

```ts
globalThis.DOMParser = new JSDOM().window.DOMParser;
```

Use a parser configuration that disables external entities and external fetching.

A call with neither is refused with `DocxImportError` and the code `no-xml-parser`, so a runtime
missing its parser reads as that rather than as a damaged file.

Nothing else about the browser is needed: no `Node` global, no `document`, no `window`.

## Verifying a commenter's file

A file returned by a `comment` editor should differ from the original in comments alone.
The editor enforces that in the browser only; check it again on the server, where the file
arrives.
`onlyCommentsChangedBy` compares the returned file with the original:

```ts
import { onlyCommentsChangedBy } from "@portone/docx-editor/core";

const verdict = onlyCommentsChangedBy(original, submitted, user.id);
if (!verdict.ok) console.warn(verdict.reason);
```

The comparison covers the whole package, not the document text alone.
Five things have to hold for a file to be accepted:

- Every part arrives byte-identical, save for the comments part, the extended comments part, and
  the people part.
- The main document part reads as it did outside its body blocks.
- Its relationships and `[Content_Types].xml` gain only what those three parts need.
- The story reads as it did with the comments taken out, and every comment that changed is this
  author's.
- Every entry of those three parts arrives as it was, or is one this editor writes and this author
  could have written. An entry nothing refers to stays as it was.

`editableComments` says whose comments may have changed.
It defaults to `"own"`, this author's comments and the ones carrying no identity; pass `"all"` for
a file that came from a moderator's editor.

The answer names what was refused rather than reporting a bare `false`, so a server can log it:

```ts
type CommentOnlyVerdict =
  | { ok: true }
  | {
      ok: false;
      reason: "body-changed" | "comment-not-owned" | "comment-author-forged";
    }
  | {
      ok: false;
      reason: "part-changed" | "relationship-changed";
      part: string;
    };
```

| `reason` | What it means |
| --- | --- |
| `body-changed` | The document differs in something other than its comments, which includes a body edit that swept a comment away with the text it was anchored to. |
| `comment-not-owned` | A comment or reply written by somebody else was rewritten, re-anchored onto other text, or deleted. |
| `comment-author-forged` | A comment that appeared claims another identity, or a comment that was already there had its author rewritten. |
| `part-changed` | A part outside the comment parts differs, the main part changed outside its body blocks, or an entry of a comment part is not one this editor writes for this author. `part` names the package path. |
| `relationship-changed` | The main part's relationships gained, lost, or repointed something that is not a comment part, gained a second relationship of a comment type, or related a part the file already held as a comment part. `part` names the relationship part. |

Two files can say the same thing in different words, so the story is compared as this editor
writes it back rather than as the two files worded it.
Two blocks this editor would write alike read alike here: the attribute order inside a `w:tcW` or
a `w:tblW`, for instance, a percentage width written as `100%` or as `5000`, runs a producer split
that say the same text, or a table's `w:tblGridChange`, which this editor drops whenever it
rebuilds a table.
A submission that changed only such a difference is accepted.

Content this editor carries through is compared, down to a comment a producer left between two
properties.
What it builds afresh is not, and there are three of those: a table's `w:tblGrid` is written from
the column widths alone, a drawing's extent from the size the model holds, and a table property the
model no longer needs is dropped along with anything inside it.
A difference confined to one of those three is not seen.
Where a file's integrity has to be checked to the byte, compare the parts themselves rather than
asking this question of them.

Run the verifier on a package at least as new as the editor that wrote the file.
The verdict accepts the shapes this editor's writer produces, so a file written by a later version
may hold a comment this one does not recognise.

[Modes and protection](/docs/custom-controls#modes-and-protection) describes the ownership rule
this holds to.

Unreadable bytes throw `DocxImportError`, as `importDocx` does.

## Errors

`DocxImportError` and `DocxExportError` expose stable `code` values for application handling. Error
messages are intended for developers and may be reworded.

```ts
import { DocxImportError, importDocx } from "@portone/docx-editor/core";

try {
  importDocx(source);
} catch (error) {
  if (error instanceof DocxImportError) {
    console.error(error.code);
  }
  throw error;
}
```

Both classes are exported from the root entry as well, so a React screen can switch on the same
codes without importing the core entry.

### Import codes

| Code | Why the document was refused |
| --- | --- |
| `no-xml-parser` | The runtime has no XML parser: no `xmlParser` was passed and there is no `DOMParser` global. |
| `not-a-docx` | The bytes are not a readable zip container, its entry names are not a package's, or an entry does not hold what it claims to. |
| `too-large` | The package asks to inflate beyond the limits below. |
| `missing-part` | The package carries no main document part. |
| `missing-body` | The main part carries no body. |
| `malformed-xml` | The XML cannot be parsed, declares a DTD, or its markup is inconsistent. |
| `unsupported-content` | The document holds markup that could not be written back out unchanged. |

`no-xml-parser` is about where the call was made rather than about the file, and a browser never
reaches it; [Server environments](#server-environments) covers it.
A file a person picked can fail with any of the rest, so the code is worth showing: `not-a-docx`
and `too-large` are usually the person's to fix, while the others describe the file itself.

### Export codes

| Code | Why the document could not be written |
| --- | --- |
| `missing-numbering-part` | A new list needs a numbering part the document does not have. |
| `missing-content-types` | A new image needs a content types part the package does not have. |
| `unsupported-content` | The document holds a node kind with no way to serialize it. |
| `lost-original` | A node that carries only its original XML has lost it. |
| `malformed-xml` | An original XML fragment cannot be read well enough to rewrite. |
| `invalid-table` | The table grid is inconsistent, such as a vertical merge outliving its rows. |

An export failure leaves the editor state untouched, so a screen can report the reason and let the
person carry on editing.
`missing-numbering-part` is the one an ordinary edit can reach: a document with no numbering part
cannot take a new list, and the built-in list controls report that they do not apply for exactly
that reason.
`malformed-xml` is not: the editor turns a raw fragment down at the DOM boundary before it reaches
the document, so this code names a fragment a plugin wrote or a bug in the editor rather than
anything a person typed.

### In the React component

The component renders a refusal in place of the editor when import fails, either through
`renderImportError` or through the built-in panel, which turns each import code into a sentence.
Only `DocxImportError` becomes a rendered refusal; anything else, a `Blob` that could not be read
included, is thrown for an error boundary above to take.
On the way out, `downloadDocx` and `exportBytes` rethrow `DocxExportError` as it is.

## Import limits

- A single inflated part is limited to 32 MiB and the package total to 64 MiB.
- Package paths that escape the archive and XML containing a DTD are rejected.
- An image over 16 MiB is retained in the package without being rendered by the editor.

## Utilities

The core entry exports the document schema (`docxSchema`), the numbering reader
(`parseNumbering`), typed format readers such as `toRunFormat` and `toParagraphFormat`, and the
unit conversions `emuToPx` and `pxToEmu` used for programmatic transforms. The published
TypeScript declarations describe the complete surface.
