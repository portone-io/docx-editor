`@portone/docx-editor/core` provides programmatic DOCX import and export without mounting an
editor. It returns a ProseMirror document together with an opaque session that retains the rest of
the DOCX package.

## Import and export

Keep the session returned by `importDocx` and pass it back to `exportDocx` with the original or
transformed document:

```ts
import { exportDocx, importDocx } from "@portone/docx-editor/core";

const { doc, session } = importDocx(source);
const bytes = exportDocx(doc, session);
```

The core functions accept an `ArrayBuffer` or `Uint8Array`. The React component also accepts a
`Blob` or `File` and reads it before import.

The session belongs to the imported document and must not be constructed or modified by consumers.
Use `documentNumbering(session)` and `documentPartPath(session)` for the package information
exposed by the public API.

`documentNumbering(session)` reads the document's lists as the editor draws them: a list that takes
its numbers from a numbering style is followed to the definition holding them, and the character
formatting each level puts on its own number is read in.
`parseNumbering(xml)` reads a numbering part handed over on its own, without the styles that go
with it, so a list defined through a numbering style is resolved only as far as that part alone
allows. Pass `links`, a numbering style id to the list it names, to resolve the rest.

## What a document loses

A DOCX holds more than this editor draws.
Markup it cannot model is carried through the round trip untouched, but some of it is invisible on
the page and some of it stands behind a placeholder nobody can edit.
`notes` says what, one entry per piece:

```ts
const { doc, session, notes } = importDocx(source);

for (const note of notes) {
  console.log(note.severity, note.code, note.element, note.block);
}
```

Each note carries how much of the original survived (`severity`), what kind of content it was
(`code`), the package path of the part it came from (`part`), the body block it falls in (`block`),
its position in the document (`pos`, which a reader can select), and the original element name
(`element`, such as `w:bookmarkStart`).

| `severity` | What it means |
| --- | --- |
| `hidden` | Carried through whole, with nothing of it on screen. A bookmark marker, for instance. |
| `placeholder` | Carried through whole behind a placeholder that stands in its place and cannot be edited. |
| `approximated` | Written back as something near what arrived rather than as what arrived. |

`code` names the content: `range-marker` for one end of a bookmark or a similar range,
`preserved-inline` and `preserved-block` for markup kept where it stood, `preserved-run-content`
for a piece of a run, and `paragraph-demoted` or `table-demoted` for a paragraph or table this
editor could not model at all.

Currently, notes cover preserved block and inline nodes, including hidden bookmarks and
placeholders. `preserved-run-content` and `approximated` are reserved for future reporting;
neither is emitted yet. An empty list does not guarantee a lossless round trip: the writer's
known losses described below are not included in these notes.

`exportDocxReport` writes the file and returns the notes for the document it wrote, so a server
can report its preserved content without opening the file again:

```ts
import { exportDocxReport } from "@portone/docx-editor/core";

const { bytes, notes } = exportDocxReport(doc, session);
```

`exportDocx(doc, session)` is those bytes and nothing else, and both take the same options.
Inside an editor, [`documentFidelity`](/docs/custom-controls#images-links-and-annotations) answers
the question about the document as it currently stands.

## Server environments

Reading a DOCX means reading the XML inside it, and that needs a parser. Browsers have one.
Anywhere else, pass one in:

```ts
import { JSDOM } from "jsdom";
import { importDocx } from "@portone/docx-editor/core";

const { DOMParser } = new JSDOM().window;

const { doc, session } = importDocx(source, { xmlParser: new DOMParser() });
```

`importDocx`, `exportDocx`, `exportProblems`, and `onlyCommentsChangedBy` all take `xmlParser`,
and the parser one of them is given reads every part it touches, including both of the files
`onlyCommentsChangedBy` opens for itself.
`documentNumbering` and `parseNumbering` read XML of their own rather than through one of those
calls, so they take the option as a second argument.
The option asks for `parseFromString(source, "application/xml")`, and what it hands back has to be
a real DOM document rather than an object shaped like one: the readers walk it with the standard
DOM API, `documentElement`, `children`, `childNodes`, `attributes`, `getAttribute` and
`getElementsByTagName` with their namespace-aware forms, `localName`, `nodeName`, `nodeType`,
`nodeValue`, `namespaceURI`, `textContent`, `parentElement`, `ownerDocument` and `cloneNode` among
them.
Markup it cannot read has to be reported the way a browser reports it, by throwing or by handing
back a document holding a `parsererror` element; either way the read is refused with
`malformed-xml`.

The package bundles no parser of its own, and jsdom is the only implementation it tests. jsdom is
the obvious one on a long-running Node server, while on serverless functions it adds noticeable
bundle weight and cold-start time and edge runtimes cannot run it at all, so treat those
environments as unsupported for now.

Installing a `DOMParser` global instead works, and every call then leaves the option out:

```ts
globalThis.DOMParser = new JSDOM().window.DOMParser;
```

Use a parser configuration that disables external entities and external fetching.

A call with neither is refused with `DocxImportError` and the code `no-xml-parser`, so a runtime
missing its parser reads as that rather than as a damaged file.

Nothing else about the browser is needed: no `Node` global, no `document`, no `window`.

## Verifying a commenter's file

A file returned by a `comment` editor should differ from the original in comments alone.
The editor enforces that in the browser only; check it again on the server, where the file
arrives.
`onlyCommentsChangedBy` compares the returned file with the original:

```ts
import { onlyCommentsChangedBy } from "@portone/docx-editor/core";

const verdict = onlyCommentsChangedBy(original, submitted, user.id);
if (!verdict.ok) console.warn(verdict.reason);
```

The comparison covers the whole package, not the document text alone.
The following must hold for a file to be accepted:

- Every part arrives byte-identical, save for the comments part, the extended comments part, and
  the people part.
- The main document part reads as it did outside its body blocks.
- Its relationships and `[Content_Types].xml` gain only what those three parts need.
- The story reads as it did with the comments taken out, and every comment that changed is this
  author's.
- Every entry of those three parts arrives as it was, or is one this editor writes and this author
  could have written. An entry nothing refers to stays as it was.
- XML comments and processing instructions outside those entries stay as they were, including
  those outside the part root. Layout whitespace may differ, and rebuilding comment entries may
  remove annotations between them; new or altered annotations are rejected.

`editableComments` says whose comments may have changed.
It defaults to `"own"`, this author's comments and the ones carrying no identity; pass `"all"` for
a file that came from a moderator's editor.

The answer names what was refused rather than reporting a bare `false`, so a server can log it:

```ts
type CommentOnlyVerdict =
  | { ok: true }
  | {
      ok: false;
      reason: "body-changed" | "comment-not-owned" | "comment-author-forged";
    }
  | {
      ok: false;
      reason:
        | "part-changed"
        | "relationship-changed"
        | "comment-markup-rejected";
      part: string;
    };
```

| `reason` | What it means |
| --- | --- |
| `body-changed` | The document differs in something other than its comments, which includes a body edit that swept a comment away with the text it was anchored to. |
| `comment-not-owned` | A comment or reply written by somebody else was rewritten, re-anchored onto other text, or deleted. |
| `comment-author-forged` | A comment that appeared claims another identity, or a comment that was already there had its author rewritten. |
| `part-changed` | A part outside the comment parts differs, or the main part changed outside its body blocks. `part` names the package path. |
| `relationship-changed` | The main part's relationships gained, lost, or repointed something that is not a comment part, gained a second relationship of a comment type, or related a part the file already held as a comment part. `part` names the relationship part. |
| `comment-markup-rejected` | An entry of a comment part is not one this editor writes for this author, or an entry nothing refers to changed. `part` names the comment part. |

Two files can say the same thing in different words, so the story is compared as this editor
writes it back rather than as the two files worded it.
Two blocks this editor would write alike read alike here: the attribute order inside a `w:tcW` or
a `w:tblW`, for instance, a percentage width written as `100%` or as `5000`, or runs a producer
split that say the same text.
A submission that changed only such a difference is accepted.

Content this editor carries through is compared, down to a comment a producer left between two
properties.
What it builds afresh is not, and there are three of those: a table's `w:gridCol` list is written
from the column widths alone, a drawing's extent from the size the model holds, and a table
property the model no longer needs is dropped along with anything inside it.
A difference confined to one of those three is not seen.
Where a file's integrity has to be checked to the byte, compare the parts themselves rather than
asking this question of them.

Run the verifier on a package at least as new as the editor that wrote the file.
The verdict accepts the shapes this editor's writer produces, so a file written by a later version
may hold a comment this one does not recognise.

[Modes and protection](/docs/custom-controls#modes-and-protection) describes the ownership rule
this holds to.

Unreadable bytes throw `DocxImportError`, as `importDocx` does.

## Errors

`DocxImportError` and `DocxExportError` expose stable `code` values for application handling. Error
messages are intended for developers and may be reworded.

```ts
import { DocxImportError, importDocx } from "@portone/docx-editor/core";

try {
  importDocx(source);
} catch (error) {
  if (error instanceof DocxImportError) {
    console.error(error.code);
  }
  throw error;
}
```

Both classes are exported from the root entry as well, so a React screen can switch on the same
codes without importing the core entry.

### Import codes

| Code | Why the document was refused |
| --- | --- |
| `no-xml-parser` | The runtime has no XML parser: no `xmlParser` was passed and there is no `DOMParser` global. |
| `not-a-docx` | The bytes are not a readable zip container, its entry names are not a package's, or an entry does not hold what it claims to. |
| `too-large` | The package asks to inflate beyond the limits below. |
| `missing-part` | The package carries no main document part. |
| `missing-body` | The main part carries no body. |
| `malformed-xml` | The XML cannot be parsed, declares a DTD, or its markup is inconsistent. |
| `unsupported-conformance` | The package is an ECMA-376 Strict one. This editor reads and writes Transitional, which is what Word saves by default. |
| `unsupported-content` | The document holds markup that could not be written back out unchanged. |

`no-xml-parser` is about where the call was made rather than about the file, and a browser never
reaches it; [Server environments](#server-environments) covers it.
A file a person picked can fail with any of the rest, so the code is worth showing: `not-a-docx`
and `too-large` are usually the person's to fix, while the others describe the file itself.
A main document root that does not bind `w` to the Transitional WordprocessingML namespace is
refused as `unsupported-content`, since the WordprocessingML writer emits that prefix.

### Checking before export

`exportProblems(doc, session)` reports known reasons `exportDocx` would refuse the document, before
anything is written and in the order the writer would raise them:

```ts
import { exportDocx, exportProblems } from "@portone/docx-editor/core";

const problems = exportProblems(doc, session);
if (problems.length > 0) {
  console.warn(problems[0].code, problems[0].message);
} else {
  const bytes = exportDocx(doc, session);
}
```

Each problem carries the `code` and `message` the `DocxExportError` would carry, and `pos` where
the problem stands at a place in the document, which a screen can select; a problem of the
package or of the session carries none.

| Code | What is reported |
| --- | --- |
| `malformed-xml` | A bookmark marker whose partner is gone, or a comment part with no root element to rewrite around once a comment has changed. |
| `invalid-table` | A vertical merge reaching past the last row of its table. |
| `lost-original` | A preserved block that has lost its original XML, or a placeholder pasted in from another open document: a placeholder is written from the file it was read out of, so one from another file cannot be. |
| `unsupported-content` | A preserved block, such as a body-level bookmark marker or an element the editor does not model, copied so that it stands in two places: there is one original to write and nothing to rebuild the second from. Reported where the second one stands. |
| `missing-numbering-part` | A new list in a document that has no numbering part to define it in. The built-in list controls report that they do not apply for exactly this reason. |
| `missing-content-types` | A new image or comment-related part, in a package that has no content types part to declare the new part in. |

The checks report these codes for the conditions they cover, and `exportDocx` throws the
first entry of the same list with its code and message. An empty list does not guarantee that
writing will succeed.
Inside an editor, [`canExport`](/docs/custom-controls#commands-and-queries) asks the same question
of the state.
A write that needs a namespace prefix already bound to a different namespace is also refused as `unsupported-content`; this includes a local declaration that changes the meaning of a newly written hyperlink.

A refusal the list does not foresee is still thrown: `unsupported-content` for a node or an image
of a kind the writer cannot put out, `lost-original` or `malformed-xml` for a node a plugin
stripped of an attribute the writer needs or a raw fragment it wrote that does not hold its shape,
and `malformed-xml` naming the part for any rewritten part of the package that does not read back
as XML, since every part the writer produces is parsed before the file is repacked.
None of those is reached by typing; each names a plugin's doing or a bug in the editor.

Writing reads the document it produced back, so `exportDocx` needs an XML parser as much as
`importDocx` does, and `exportProblems` reads the list definitions to tell a new list from one the
document already had, so it takes the same `xmlParser` option.
A call on a runtime with none is refused ahead of all of these, with `DocxImportError` and the
import code `no-xml-parser`; [Server environments](#server-environments) covers it.

An export failure leaves the editor state untouched, so a screen can report the reason and let the
person carry on editing.

### In the React component

The component renders a refusal in place of the editor when import fails, either through
`renderImportError` or through the built-in panel, which turns each import code into a sentence.
Only `DocxImportError` becomes a rendered refusal; anything else, a `Blob` that could not be read
included, is thrown for an error boundary above to take.
On the way out, `downloadDocx` asks the list above first and returns `blocked` with the problems
rather than throwing, while `exportBytes` throws `DocxExportError` as it is; a refusal the list
did not foresee is thrown by both.

## Import limits

- A single inflated part is limited to 32 MiB and the package total to 64 MiB.
- Package paths that escape the archive and XML containing a DTD are rejected.
- An image over 16 MiB is retained in the package without being rendered by the editor.

## Utilities

The core entry exports the document schema (`docxSchema`), the numbering reader
(`parseNumbering`), typed format readers such as `toRunFormat` and `toParagraphFormat`, and the
unit conversions `emuToPx` and `pxToEmu` used for programmatic transforms. The published
TypeScript declarations give their signatures, and
[What a plugin may rely on](/docs/custom-controls#what-a-plugin-may-rely-on) says which parts of the
document model hold across releases and which are this editor's own bookkeeping.
