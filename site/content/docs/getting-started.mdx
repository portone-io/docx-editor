Six steps from an empty React project to a document a person can edit and download.

<Steps>

<Step>

## Install the package

```sh
npm i @portone/docx-editor
```

</Step>

<Step>

## Import the stylesheet

```ts
import "@portone/docx-editor/styles.css";
```

Once per application is enough, and the import carries the ProseMirror base styles the editor
needs.
[Styling](/docs/styling) covers the custom properties that restyle the frame around the paper.

</Step>

<Step>

## Get a document to open

`document` takes a `File`, a `Blob`, an `ArrayBuffer`, or a `Uint8Array`, so the file arrives
however your application already holds it.
A document fetched from a server needs no more than its response body:

```ts
const response = await fetch("/agreement.docx");
const file = new File([await response.blob()], "agreement.docx");
```

Bytes open immediately; a `Blob` or a `File` is read first, so the editor stands empty for that
moment.

</Step>

<Step>

## Mount the editor

Render `DocxEditor` with the document and a `mode`, and keep a ref if the surrounding screen will
export it:

```tsx
import { DocxEditor, type DocxEditorHandle } from "@portone/docx-editor";
import { useRef } from "react";

export function Editor({ file }: { file: File }) {
  const editorRef = useRef<DocxEditorHandle | null>(null);

  return (
    <DocxEditor
      ref={editorRef}
      document={file}
      mode={{ kind: "edit", author: { id: user.id, name: user.name } }}
    />
  );
}
```

`mode` says what the editor is for - a reader's surface, a commenter's, or an editor's - and
`author` names the person its comments are written under, taken from your application's signed-in
user.
[Props](/docs/props#mode) describes the kinds, and [Modes](/docs/features/modes) what each lets a
person do.
The editor fills the height it is given, so put it in a box with one.

</Step>

<Step>

## Export the edited document

`downloadDocx` takes the handle from the ref and saves the current editor state as a file.
It reports `unavailable` while no document is open yet and `empty` when there is nothing worth
exporting.

```tsx
import { downloadDocx } from "@portone/docx-editor";

const download = () => {
  const result = downloadDocx(editorRef.current, { fileName: file.name });
  if (result.status === "blocked") {
    console.warn(result.problems.map((problem) => problem.code));
  }
};

<button onClick={download} type="button">
  Export .docx
</button>;
```

`downloadDocx` returns `blocked` with the problems when the document cannot be written back
safely, each under the code a `DocxExportError` would carry, so the surrounding screen can show
the reason; anything the check did not foresee is still thrown as `DocxExportError`.
For the bytes without a browser download, call `editorRef.current.exportBytes()`, and for the
same problems ahead of it, `editorRef.current.exportProblems()`.

</Step>

<Step>

## Check what you see

An opened document shows its own paper: the page size and margins it declares, its fonts, and its
own styles, with approximate page boundaries drawn over the text and the built-in toolbar above it.
Exporting and reopening the file in Word is the real check, since the round trip is what the editor
is for.

If a refusal panel appears in place of the editor, the document was not opened, and the panel names
the reason.
Pass `renderImportError` to write that refusal in your own words; without it the built-in panel is
drawn, so a refused document is never silent.
[Errors](/docs/core/errors) lists the codes behind those refusals.

</Step>

</Steps>

## Next.js and other prerendering frameworks

The editor builds a ProseMirror view against the DOM, so it cannot render on the server.
In a framework that prerenders, load it from a client component through a dynamic import with
server rendering turned off, which is how this site mounts its own demo:

```tsx
"use client";

import dynamic from "next/dynamic";

const Editor = dynamic(() => import("./Editor").then((m) => m.Editor), {
  ssr: false,
});
```

Fetch the document from inside that client component too, in an effect, and wrap the response in a
`File` as in the third step above.
The App Router also wants `@portone/docx-editor` in `transpilePackages` when it resolves to
TypeScript sources rather than to built output, which is the case for a workspace link.
