`DocxEditor` can keep its editing surface while a host application replaces the built-in toolbar
and context menus.

## Hide the built-in controls

`mode.toolbar` turns the toolbar off, and `contextMenus`, a prop of its own, leaves the right
button to the browser:

```tsx
<DocxEditor
  document={file}
  mode={{
    kind: "edit",
    author: { id: user.id, name: user.name },
    toolbar: false,
  }}
  contextMenus={false}
/>
```

A `comment` editor has no toolbar to hide, and its right-click menu is already cut down to Copy and
Add comment.

## Commands and queries

Text and paragraph commands come from `@portone/docx-editor/commands`. Operations on an existing
table come from `@portone/docx-editor/table`, while `insertTable` comes from
`@portone/docx-editor/commands`.

Commands follow the ProseMirror command contract. Calling one with an `EditorState` reports whether
it applies, while passing a dispatch function performs the edit.

```tsx
import type {
  Command,
  EditorState,
  EditorView,
} from "@portone/docx-editor";
import { isBoldActive, toggleBold, undo } from "@portone/docx-editor/commands";

function Toolbar({ view, state }: { view: EditorView; state: EditorState }) {
  const run = (command: Command) => {
    command(state, (transaction) => view.dispatch(transaction), view);
    view.focus();
  };

  return (
    <div>
      <button
        type="button"
        aria-pressed={isBoldActive(state)}
        onClick={() => run(toggleBold)}
      >
        Bold
      </button>
      <button type="button" disabled={!undo(state)} onClick={() => run(undo)}>
        Undo
      </button>
    </div>
  );
}
```

`onReady` provides the editor view, and `onChange` fires whenever the editor state changes. Use
both to keep custom controls in sync with the current selection.

The query prefixes describe what they return:

- `is*Active` reports a boolean toggle.
- `active*` reports the current value or a mixed selection.
- `can*` reports whether the related action applies.
- `isIn*` reports containment.

`DEFAULT_X` names the built-in default for the prop or field named `x`. Selection-level readers use
`selection*`, while document-level readers use `document*`. A reader of the protection the editor
itself runs under, which the document does not record, uses `editing*`.

Package commands account for locked content, for the editor's mode, and for the content the editor
preserves rather than edits before reporting that they apply, so a control built on them is disabled
exactly where the edit would be refused. Preserved bookmark markers and note references are part of
that: neither can be put back once it is gone, so a command that would sweep one away reports that
it does not apply. Wrap third-party or application commands with `canRunCommand(command, state)`
when they also need to respect the same rules.

`canExport` reports whether the document as it stands can be written back, and
`documentExportProblems` lists every reason it could not, each under the code `DocxExportError`
would carry and with its `pos` where the problem stands in the document, so an export control is
drawn from the same list the writer refuses over; [Checking before
export](/docs/core#checking-before-export) lists the codes.

Use `insertTab` to insert the same editable DOCX tab as the built-in Tab binding. It applies inside
an ordinary paragraph; table cells and list paragraphs keep their navigation and level-changing Tab
behavior.

## Tables

Table-cell controls use `canSetCellFormatting`, `activeCellVerticalAlign`, `setCellVerticalAlign`,
`activeCellPadding`, and `setCellPadding`. The gate query covers the whole selection, alignment
reports `top`, `center`, `bottom`, or `mixed`, and each padding side independently reports a point
value, `mixed`, or `null`. A padding command writes only the sides supplied. `activeCellBorderColor`,
`canSetCellBorderColor`, and `setCellBorderColor` operate on effective visible borders; editing a
border inherited from its table or table style creates a direct override only on the visible sides
of the selected cells.

## Images, links, and annotations

Image controls can use `IMAGE_FILE_ACCEPT`, `imageFilesIn`, and `insertImageFiles`. Lower-level
controls can combine `readImageFile`, `fittedExtent`, and `insertImage`.

Link controls use `canSetLink`, `activeLink`, `activeLinkSpan`, `setLink`, and `removeLink`.
External links are editable; bookmark links remain preserved.

Comment controls use `canAddComment`, `addComment`, `documentComments`, `selectComment`,
`updateComment`, `setCommentBody`, `removeComment`, `addCommentReply`, `updateCommentReply`,
`removeCommentReply`, and `setCommentResolved`. `mode.author` is the identity the built-in composers write; a composer of
your own passes `author` (the display name), `initials`, and `authorId` taken from `mode.author` to
`addComment` and `addCommentReply`, so that the comment is recorded as that person's.
`documentComments` reports `authorId` on every comment and reply, and `canEditComment` answers
whether the current author may edit or delete one; [Modes and
protection](#modes-and-protection) explains the rule behind it. Every field of the records it
returns is read-only: they are the editor's own, worked out once per edit, so a control that wants
to change one copies it rather than writing into it.

A comment body keeps its formatting. `updateComment` replaces one with plain text; `setCommentBody`
replaces one with a document of `docxSchema`, so a composer of your own can write a body with a
bold run, a paragraph style, or a second paragraph:

```ts
import { docxSchema } from "@portone/docx-editor";
import { setCommentBody } from "@portone/docx-editor/commands";

const body = docxSchema.nodes.doc.create(null, [
  docxSchema.nodes.paragraph.create(null, [
    docxSchema.text("Please check", [
      docxSchema.marks.run.create({ rPr: "<w:rPr><w:b/></w:rPr>" }),
    ]),
  ]),
  docxSchema.nodes.paragraph.create(null, docxSchema.text("the second line.")),
]);

setCommentBody(comment.id, body)(view.state, view.dispatch);
```

The command answers `false` for a body that is not a `doc` node, one that reads as nothing but
whitespace, and an id the document refers to no comment for. Whatever the body does not touch is
written back as the bytes it arrived as, so a paragraph nobody edited keeps everything about it the
editor does not model.

`addComment` and `canAddComment` take an optional `{ from, to }` range as their last argument, and
use the current selection when none is given. The range must use integer document positions and
cover a non-empty span inside one paragraph; invalid ranges return `false` without dispatching.
Pass one from a composer of your own that stays open while the document is edited: keep the range
you opened it over, map it through `transaction.mapping` on every change, and hand that range to
`addComment` when the writer submits, so the comment marks the text it was written about rather
than wherever the caret has since gone.

`documentNotes` returns the distinct footnotes and endnotes referenced by the main document,
including their display labels and the plain text their bodies read as. Its records are read-only
for the same reason the comment records are.

`documentFidelity` returns what the open document holds that the editor cannot model: markup that
is preserved but invisible, and the placeholders standing in for content it could not open for
editing.
Each note carries a `pos`, so a panel listing them can move the selection to the one a reader picks.
The list is read off the document as it stands, so a note goes as soon as an edit takes away what
it was about.
[Core API](/docs/core#what-a-document-loses) describes the note fields, and returns the same list
from `importDocx` and `exportDocxReport`.

## Document zoom

The editor fits the page to its available width by default. Its toolbar offers Fit, 50%, 75%,
100%, 125%, and 150%. Fixed zoom remains selected on a narrow screen and makes the document
horizontally scrollable instead of forcing it back to fit.

Use `defaultZoom` when the editor should own the selection, or `zoom` with `onZoomChange` when the
host should own it:

```tsx
import { DocxEditor, type DocxEditorZoom } from "@portone/docx-editor";
import { useState } from "react";

const author = { id: user.id, name: user.name };

function Preview({ file }: { file: File }) {
  const [zoom, setZoom] = useState<DocxEditorZoom>("fit-width");

  return (
    <DocxEditor
      document={file}
      mode={{ kind: "edit", author }}
      zoom={zoom}
      onZoomChange={setZoom}
    />
  );
}
```

Numeric values from `0.25` through `2` are accepted. The root entry exports `DEFAULT_ZOOM_LEVELS`
for a custom toolbar. A read-only or comment editor has no built-in toolbar, but a host can still
set `zoom`.
Zoom changes only the browser presentation; it does not change pagination measurements, the
document model, or exported OOXML. Persisting a reader's choice belongs to the host application.

The comment panel reads the same factor from the `--docx-editor-zoom` custom property, set on the
editor workspace, so comment text scales with the paper instead of standing apart from it. Its font
sizes stop shrinking at a readable floor, and the panel keeps its width at every zoom level.

## Modes and protection

`mode.kind` puts the editor under a protection:

| `mode.kind` | What goes through |
| --- | --- |
| `readOnly` | Nothing. The text can be selected and copied; comments can be read. |
| `comment` | Comments alone: adding, editing, deleting, replying, resolving, and reopening. |
| `edit` | Everything. |

The kinds are named after OOXML's document protection levels, but nothing is written to the file;
a `w:documentProtection` the document carries is preserved as it is.

Under `comment` a formatting command reports `false`, `canAddComment` still reports `true` over a
selection, and undo takes back a comment but not a body edit, from the keyboard as well as from
the panel.
A [lock](#locked-content) is refused the same way.
A control of your own reads the level with `editingProtection`:

```tsx
import {
  canEditComment,
  editingProtection,
} from "@portone/docx-editor/commands";

const level = editingProtection(state); // "none" | "readOnly" | "comments"
const mine = canEditComment(state, comment.id); // or (state, comment.id, reply.id)
```

`canEditComment` answers whether the current author may edit or delete a comment or one of its
replies.
A comment records the identity it was written under in the document's `people.xml` part, the way
Word does. The rule is:

- A comment carrying a recognized identity belongs to that author. Nobody else is offered Edit or
  Delete on it, and an edit a control offers anyway is refused.
- A comment carrying no identity, one written in Word or before identities were recorded, belongs
  to everyone.
- Re-anchoring a comment onto other text counts as editing that comment, so somebody else's is
  refused.
- A comment's author never changes after it is written, its own author included; only a new
  comment chooses an identity.
- `mode.editableComments: "all"` opens every comment to the current author.
- Replying, resolving, and reopening never depend on ownership; under `comment` and `edit` they
  are open to everyone.
- Deleting a root comment deletes its replies, whoever wrote them, because a thread hangs off its
  root.

A server that takes a commenter's file back checks the same rule with
[`onlyCommentsChangedBy`](/docs/core#verifying-a-commenters-file), which holds the file against the
very policy the editor writes comments under, so what the editor offers and what the server takes
back cannot drift apart.

## Locked content

A lock is an OOXML content control that shuts its contents, so it is part of the document rather
than editor state: it survives a round trip and travels with the file.
A lock the open document already carries is honored in every mode, `readOnly` and `comment`
included, and no prop turns it off.
What `mode: { kind: "edit", locking: true }` adds is the authoring side, the built-in menu entries
that put a lock on and take one off, since settling part of a document is a template author's act
rather than something every reader of a form should be handed.

Custom controls read the selection with `selectionLock`, which answers with one of four states
instead of a pair of booleans a menu has to combine:

```tsx
import {
  lockSelection,
  selectionLock,
  unlockSelection,
} from "@portone/docx-editor/commands";

const lock = selectionLock(state); // "none" | "lockable" | "locked" | "mixed"
```

`lockable` means there is text to shut, `locked` that the selection reaches a lock to lift, and
`mixed` that it does both.
`lockSelection` and `unlockSelection` are ordinary commands, so each reports whether it applies
before it is offered.

Locking wraps one control per paragraph the selection runs through, and only a text selection has
anything to lock: a selected image or a block of table cells is not a stretch of text a control can
hold.
Reaching the edge of a control counts as reaching it, so a caret resting against either end of a
locked field, or anywhere inside a locked cell, is enough to unlock it.
A lock is lifted whole, and unlocking keeps the control itself, removing only its lock.

`selectionTouchesLocked(state)` answers whether the selection meets locked content at all, which is
what a control outside this package asks before editing.
`documentHasLocked(doc)` takes the document rather than the state and reports whether the file
carries any lock, which is how a screen decides to show its locking affordances at all.

## Presets and plugins

The root entry exports the preset values used by the built-in controls, including `DEFAULT_COLORS`,
`DEFAULT_FONT_SIZES`, `DEFAULT_LINE_SPACINGS`, `DEFAULT_CELL_BORDERS`, and `DEFAULT_FONTS`. Pass
replacement lists through the `presets` prop when the built-in controls should offer different
values. Color presets remain quick choices; the built-in color controls also accept any three- or
six-digit HEX color.

Pass ProseMirror plugins through the `plugins` prop. Consumer keymaps receive keyboard events
before the built-in keymap, so an application can override bindings such as `Mod-k` without
replacing the editor.

A plugin that writes raw OOXML into a node or mark attr, such as a paragraph's `pPr`, a run's
`rPr`, or a content control's opening tag, has to write the shape that attr goes back out as: a
single element under the name the attr carries, the attributes of an opening tag on their own, or
an opening tag with nothing inside it yet. The editor reads the page back after an IME composition
or a browser edit, and a fragment that is none of those is turned down there, taking its node or
mark down one level with it. A paragraph then keeps its text and loses its properties, a run loses
its formatting, and a content control or a hyperlink loses its wrapper.

## What a plugin may rely on

The supported plugin surface includes the node and mark names of `docxSchema`, `srcId`, the
`format` attrs and their `to*Format` readers, and the names and types exported by the four entry
points. Changes to this surface follow the package's public API versioning policy.
Treat `srcId` as an opaque reference within the session that opened the document; its value is not
a persistent identifier across imports.

Raw OOXML attrs such as `pPr`, `rPr`, `tcPr`, `xml`, `sdtPrefix`, `linkPrefix`, and `commentXml` are
internal and may change in any release. Prefer commands and typed format readers to depending on
their names or writing them directly.

The DOM checks described above run when the editor reads the page back. A programmatic node edit
can bypass that path. Export checks XML well-formedness and selected document invariants, but does
not validate every raw attr against its expected shape or the full OOXML schema. Handwritten attrs
can therefore cause an export error or produce an invalid DOCX file.

See [Features](/docs/features) for behavioral limits and the published TypeScript declarations for
complete signatures.
