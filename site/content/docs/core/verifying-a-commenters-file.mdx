---
title: Verifying a commenter's file
description: Check on the server that a file returned by a comment editor differs from the original in comments alone.
---

A file returned by a `comment` editor should differ from the original in comments alone.
The editor enforces that in the browser only; check it again on the server, where the file arrives.
`onlyCommentsChangedBy` compares the returned file with the original:

```ts
import { onlyCommentsChangedBy } from "@portone/docx-editor/core";

const verdict = onlyCommentsChangedBy(original, submitted, user.id);
if (!verdict.ok) console.warn(verdict.reason);
```

## What must hold

The comparison covers the whole package, not the document text alone.
The following must hold for a file to be accepted:

- Every part arrives byte-identical, save for the comments part, the extended comments part, and the people part.
- The main document part reads as it did outside its body blocks.
- Its relationships and `[Content_Types].xml` gain only what those three parts need.
- The story reads as it did with the comments taken out, and every comment that changed is this author's.
- Every entry of those three parts arrives as it was, or is one this editor writes and this author could have written.
  An entry nothing refers to stays as it was, and adding a person cannot assign an identity to an existing unattributed comment, including one outside the editable story.
- XML comments and processing instructions outside those entries stay as they were, including those outside the part root.
  Layout whitespace may differ, and rebuilding comment entries may remove annotations between them; new or altered annotations are rejected.

`editableComments` says whose comments may have changed.
It defaults to `"own"`, this author's comments and the ones carrying no identity; pass `"all"` for a file that came from a moderator's editor.

## The verdict

The answer names what was refused rather than reporting a bare `false`, so a server can log it:

```ts
type CommentOnlyVerdict =
  | { ok: true }
  | {
      ok: false;
      reason: "body-changed" | "comment-not-owned" | "comment-author-forged";
    }
  | {
      ok: false;
      reason:
        | "part-changed"
        | "relationship-changed"
        | "comment-markup-rejected";
      part: string;
    };
```

| `reason` | What it means |
| --- | --- |
| `body-changed` | The document differs in something other than its comments, which includes a body edit that swept a comment away with the text it was anchored to. |
| `comment-not-owned` | A comment or reply written by somebody else was rewritten, re-anchored onto other text, or deleted. |
| `comment-author-forged` | A comment that appeared claims another identity, or a comment that was already there had its author rewritten. A comment that appeared claiming no identity at all is taken only under a display name the original file already writes an unattributed comment under, and refused under any other. |
| `part-changed` | A part outside the comment parts differs, or the main part changed outside its body blocks. `part` names the package path. |
| `relationship-changed` | The main part's relationships gained, lost, or repointed something that is not a comment part, gained a second relationship of a comment type, or related a part the file already held as a comment part. `part` names the relationship part. |
| `comment-markup-rejected` | An entry of a comment part is not one this editor writes for this author, or an entry nothing refers to changed. `part` names the comment part. |

## How files are compared

Two files can say the same thing in different words, so the story is compared as this editor writes it back rather than as the two files worded it.
Two blocks this editor would write alike read alike here: the attribute order inside a `w:tcW` or a `w:tblW`, for instance, a percentage width written as `100%` or as `5000`, or runs a producer split that say the same text.
A submission that changed only such a difference is accepted.

Content this editor carries through is compared, down to a comment a producer left between two properties.
What it builds afresh is not, and there are three of those: a table's `w:gridCol` list is written from the column widths alone, a drawing's extent from the size the model holds, and a table property the model no longer needs is dropped along with anything inside it.
A difference confined to one of those three is not seen.
Where a file's integrity has to be checked to the byte, compare the parts themselves rather than asking this question of them.

Run the verifier on a package at least as new as the editor that wrote the file.
The verdict accepts the shapes this editor's writer produces, so a file written by a later version may hold a comment this one does not recognise.

[Who may edit a comment](/docs/editor-api/comments-and-notes#who-may-edit-a-comment) describes the ownership rule this holds to.

Unreadable bytes throw `DocxImportError`, as `importDocx` does.
