Everything on this page comes from `@portone/docx-editor/commands`.

## Comment commands

| Command | What it does |
| --- | --- |
| `addComment(comment, at?)` | Adds a comment to a stretch of text: the one named, or the current selection. |
| `canAddComment(state, at?)` | Whether that stretch, or the current selection, can receive one. |
| `updateComment(id, text)` | Replaces a comment's body with plain text. |
| `setCommentBody(id, body)` | Replaces a comment's body with a formatted one. |
| `removeComment(id)` | Deletes a comment and, with it, its replies. |
| `addCommentReply(id, reply)` | Adds a reply and reopens the thread when it was resolved. |
| `updateCommentReply(commentId, replyId, text)` | Replaces a reply's body with plain text. |
| `removeCommentReply(commentId, replyId)` | Deletes one reply. |
| `setCommentResolved(id, resolved)` | Marks a thread resolved or open without deleting it. |
| `selectComment(id)` | Moves the selection to what a comment marks. |

`NewComment` is what `addComment` and `addCommentReply` take: the `text`, the `author` shown on it,
and optionally `authorId`, `initials`, and a `date` as an ISO 8601 string, which is the current
time when it is left out.

`mode.author` is the identity the built-in composers write; a composer of your own passes `author`
(the display name), `initials`, and `authorId` taken from `mode.author` to `addComment` and
`addCommentReply`, so that the comment is recorded as that person's.

## Comment records

`documentComments(state)` returns every comment in document order, each as a `DocumentComment`:

| Field | What it holds |
| --- | --- |
| `id` | The comment's id, which every other command takes. |
| `author`, `authorId`, `initials` | Who wrote it, as the document records them. Null where the document names none. |
| `date` | When it was written, as the document records it. Null where the document names none. |
| `text` | What the body reads as, as plain text. |
| `from`, `to` | The stretch it marks. |
| `referencePos` | Where its reference stands in the document. |
| `anchored` | Whether it still marks a stretch of text. |
| `resolved` | Whether the thread is settled. |
| `replies` | Its replies, each a `DocumentCommentReply` with `id`, `author`, `authorId`, `initials`, `date`, and `text`. |

Every field of the records it returns is read-only: they are the editor's own, worked out once per
edit, so a control that wants to change one copies it rather than writing into it.

`anchored` is `false` for a comment that no longer marks a stretch of the document because its text
was deleted. Such a detached comment reports `from` and `to` at its reference, and `selectComment`
takes the caret there rather than selecting anything; for an anchored comment it selects the
commented text and scrolls it into view.
[Features](/docs/features/comments-and-notes) describes what the built-in panel does with detached
and resolved comments.

## Formatted bodies

A comment body keeps its formatting. `updateComment` replaces one with plain text; `setCommentBody`
replaces one with a document of `docxSchema`, so a composer of your own can write a body with a
bold run, a paragraph style, or a second paragraph:

```ts
import { docxSchema } from "@portone/docx-editor";
import { setCommentBody } from "@portone/docx-editor/commands";

const body = docxSchema.nodes.doc.create(null, [
  docxSchema.nodes.paragraph.create(null, [
    docxSchema.text("Please check", [
      docxSchema.marks.run.create({ rPr: "<w:rPr><w:b/></w:rPr>" }),
    ]),
  ]),
  docxSchema.nodes.paragraph.create(null, docxSchema.text("the second line.")),
]);

setCommentBody(comment.id, body)(view.state, view.dispatch);
```

The command answers `false` for a body that is not a `doc` node, one that reads as nothing but
whitespace, and an id the document refers to no comment for. Whatever the body does not touch is
written back as the bytes it arrived as, so a paragraph nobody edited keeps everything about it the
editor does not model.

`updateComment` says what a comment should read as and nothing about how it is written, so it
answers `false` for the text a comment already reads as and leaves the body it has - its bold run
and its second paragraph included - rather than flattening it to the single run that text spells.
`updateCommentReply` answers the same way. Write a body out to change how it is written.

## Commenting on a range

`addComment` and `canAddComment` take an optional `{ from, to }` range as their last argument, and
use the current selection when none is given. The range must use integer document positions and
cover a non-empty span inside one paragraph; invalid ranges return `false` without dispatching.
Pass one from a composer of your own that stays open while the document is edited: keep the range
you opened it over, map it through `transaction.mapping` on every change, and hand that range to
`addComment` when the writer submits, so the comment marks the text it was written about rather
than wherever the caret has since gone.

## Who may edit a comment

`canEditComment(state, commentId, replyId?)` answers whether the current author may edit or delete
a comment or one of its replies.
A comment records the identity it was written under in the document's `people.xml` part, the way
Word does. The rule is:

- A comment carrying a recognized identity belongs to that author. Nobody else is offered Edit or
  Delete on it, and an edit a control offers anyway is refused.
- A comment carrying no identity, one written in Word or before identities were recorded, belongs
  to everyone.
- Re-anchoring a comment onto other text counts as editing that comment, so somebody else's is
  refused.
- A comment's author never changes after it is written, its own author included; only a new
  comment chooses an identity.
- `mode.editableComments: "all"` opens every comment to the current author.
- Replying, resolving, and reopening never depend on ownership; under `comment` and `edit` they
  are open to everyone.
- Deleting a root comment deletes its replies, whoever wrote them, because a thread hangs off its
  root.

A server that takes a commenter's file back checks the same rule with
[`onlyCommentsChangedBy`](/docs/core/verifying-a-commenters-file), which holds the file against the
very policy the editor writes comments under, so what the editor offers and what the server takes
back cannot drift apart.

## Footnotes and endnotes

`documentNotes(state)` returns the distinct footnotes and endnotes referenced by the main document,
in first-reference order. Each `DocumentNote` carries its `kind` (`"footnote"` or `"endnote"`), its
`id`, the `label` it is displayed with, the `text` its body reads as, and the `referencePos` where
the reference stands, so a panel listing them can move the selection to the one a reader picks.
Its records are read-only for the same reason the comment records are.
